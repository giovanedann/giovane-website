## Why I Built This

I wanted a personal website that wasn't just another portfolio template. Three distinct audiences, three distinct experiences:

- **Engineers** → A blog with technical posts (you're here)
- **Recruiters** → An interactive career journey
- **Wanderers** → A typing roguelike game (yes, really)

The challenge: build it fast, build it right, and actually ship it.

## The Tool: Claude Code

I used Claude Code for the entire development process. Not as a code generator that I copy-paste from—but as a collaborator I could iterate with in real-time.

The key insight: **the quality of the output directly mirrors the quality of the input**.

## What Made My Prompts Work

Looking back at the conversation, a few patterns emerged:

### 1. Context First, Then Action

Instead of jumping straight to "build me a landing page," I started by pointing Claude to my `CLAUDE.md` file—a document containing project requirements, tech stack decisions, and conventions.

This meant every response was grounded in the project's reality, not generic assumptions.

### 2. Reference Real Sources

When I wanted the Aceternity UI background-boxes component, I didn't describe it—I linked directly to the documentation. Claude fetched it and adapted it to our codebase.

```
I want you to use the background-boxes component of aceternity ui.
Here is the component link: https://ui.aceternity.com/components/background-boxes
```

No ambiguity. No hallucinated APIs.

### 3. Iterate in Small Steps

Rather than asking for everything at once, I made small requests and refined:

1. "Add the background boxes" → Done
2. "The boxes are too small, make them bigger" → Done
3. "Remove the plus signs" → Done
4. "The background is too blue, make it blacker" → Done

Each step was a chance to see the result and course-correct.

### 4. Voice Opinions, Ask for Feedback

When I wasn't sure about something, I asked:

> "What do you think about my prompts? Are they good to teach people how to use Claude Code?"

And when I disagreed with a choice (like naming a component `MotionButton`), I said so:

> "You can change the name of the button to only Button. MotionButton it's okay, but it's a general purpose button..."

This collaborative back-and-forth led to better architectural decisions.

### 5. Use CSS Variables, Not Hardcoded Colors

One lesson that came from iteration: I initially used direct Tailwind colors (`bg-slate-900`, `text-white`). Claude suggested—and I agreed—to use shadcn CSS variables instead (`bg-background`, `text-foreground`).

Why? Future-proofing. If I ever want to change the theme, I change one file, not fifty.

## The Stack

What we ended up with:

- **Next.js 16** (App Router)
- **TypeScript** (strict mode)
- **Tailwind CSS 4**
- **shadcn/ui** (base components, extended with motion)
- **Aceternity UI** (animated components, added on demand)
- **Motion** (formerly Framer Motion)
- **MDX** (for this blog)

## What I Learned

1. **Treat AI as a collaborator, not a generator.** Ask for opinions. Push back. Iterate.

2. **Good prompts are specific.** Link to docs. Reference files. Give context.

3. **Small iterations beat big requests.** You can't review what you can't see.

4. **Course corrections are cheap.** The cost of saying "actually, change that" is near zero.

5. **Document your decisions.** The `CLAUDE.md` file became the source of truth that kept everything consistent.
